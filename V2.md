# Huntarr v2 (Development Preview)

This document describes the `v2/` application: a standalone rewrite that
lives alongside v1 (`main.py`, `src/`) without touching it. v1 continues to
run exactly as before - v2 has its own dependencies, its own database, its
own Docker image, and its own port.

**Current milestone: foundation only.** This is a configuration and data
model preview. It does **not** search, grab, download, or import anything.
See [Non-goals](#non-goals--current-limitations) below.

## Architecture

`v2/` is a small layered Flask app:

```
v2/
  app/
    domain/       plain dataclasses + validation, zero I/O
      arr_library.py       ArrLibrary, ARR_TYPES, validate_library_input
      automation_policy.py AutomationPolicy, BALANCED_DEFAULTS, validate_policy_input
      activity.py          ActivityJob, JOB_STATES
    services/      use-case orchestration over domain + persistence
      library_service.py, policy_service.py, activity_service.py, status_service.py
    adapters/       boundary transforms
      redaction.py  strips api_key before any HTTP response
    persistence/    SQLite schema + repositories (stdlib sqlite3, no ORM)
      database.py, library_repository.py, policy_repository.py, activity_repository.py
    api/            JSON API blueprint, mounted at /api/v2
    web/            server-rendered UI shell (Jinja2 + vanilla JS/CSS, no build step)
  config.py         env-driven runtime config
  run.py            entry point (Flask dev server)
  requirements.txt  runtime deps (Flask + CVE-pinned Werkzeug/Jinja2)
  requirements-dev.txt  adds pytest
  tests/            pytest suite (unit + Flask test-client integration)
```

Data flows one direction: `web`/`api` call into `services`, `services` call
into `persistence` and use `domain` for validation, `adapters` sit at the
HTTP boundary to redact secrets. Nothing in `domain` or `persistence` knows
about Flask.

### Domain model

- **ArrLibrary** - a configured connection to one of six *Arr ecosystems:
  `sonarr`, `radarr`, `lidarr`, `readarr`, `whisparr`, `eros`. Fields:
  `name`, `type`, `url`, `api_key`, `enabled`. Persisted in SQLite via
  `LibraryRepository`, full CRUD exposed at `/api/v2/libraries`.
  **`api_key` is never present in list/detail API responses** - the
  `redact_library`/`redact_libraries` adapter strips it and exposes a
  `has_api_key` boolean instead. This is enforced by
  `tests/test_redaction.py`, including a raw-response-body substring check.

- **AutomationPolicy** - a single global policy row describing how a future
  search engine should behave: `missing_enabled`, `upgrades_enabled`,
  `cycle_interval_minutes`, `hourly_api_cap`, `successful_grab_target`,
  `dispatch_interval_seconds`, `queue_target`, `cooldown_minutes`,
  `search_order` (`sequential`/`random`/`oldest_first`/`newest_first`).
  Seeded with "Balanced" defaults on first read. Validated on every write
  (range checks, type checks); `AutomationPolicy.summary()` renders a
  plain-language description, also returned by `GET/PUT /api/v2/policy`.

- **ActivityJob** - a durable row tracking one unit of hunting work through
  `planned -> searching -> selected -> sent -> downloading -> importing ->
  verifying -> completed`, with `deferred`, `failed`, `rolled_back` as
  off-path outcomes. The API is **read-only**
  (`GET /api/v2/activity`, `GET /api/v2/activity/<id>`) and the table is
  never seeded - it starts empty and only a future search engine (or a
  test, via `ActivityRepository.create`) writes to it.

### Persistence

Plain `sqlite3` (stdlib), one short-lived connection per operation, schema
created idempotently via `CREATE TABLE IF NOT EXISTS` on startup
(`Database.init_schema`). No migration framework yet - not needed at this
scale, and the schema is additive-only so far.

### API surface

| Method | Path                        | Purpose                                  |
|--------|-----------------------------|-------------------------------------------|
| GET    | `/health`                   | Liveness + DB connectivity                |
| GET    | `/api/v2/status`             | DB health + configured/enabled library counts |
| GET/POST | `/api/v2/libraries`        | List / create libraries (redacted)        |
| GET/PUT/DELETE | `/api/v2/libraries/<id>` | Read / update / delete one library   |
| GET/PUT | `/api/v2/policy`            | Read / update the automation policy       |
| GET    | `/api/v2/activity`           | List activity jobs (filter by `?state=`)  |
| GET    | `/api/v2/activity/<id>`      | Read one activity job                     |

### Web UI

Four pages (Overview, Libraries, Activity, Settings), server-rendered
Jinja2 templates with a small vanilla-JS `fetch()` layer (`app/web/static/app.js`)
calling the JSON API above. No frontend build step or CDN dependency - the
whole UI ships as static files inside the Flask app. Every page carries a
persistent banner: *"Huntarr v2 - Development Preview. Configuration UI
only; automated hunting is not active yet."*

## Running it

### Locally

```bash
cd v2
python3 -m venv .venv
./.venv/bin/pip install -r requirements-dev.txt   # includes runtime deps + pytest
./.venv/bin/python run.py                          # serves on :9706
```

Config is entirely environment-driven (see `config.py`):

| Variable | Default | Purpose |
|---|---|---|
| `HUNTARR_V2_DB_PATH` | `data-v2/huntarr_v2.db` | SQLite file path |
| `HUNTARR_V2_HOST` | `0.0.0.0` | Bind host |
| `HUNTARR_V2_PORT` | `9706` | Bind port |
| `HUNTARR_V2_DEBUG` | `false` | Flask debug mode |

### Tests

```bash
cd v2
./.venv/bin/python -m pytest tests/ -v
```

40 tests, all passing as of this milestone: health/status, secret
redaction (including a raw-body substring assertion), policy
validation + plain-language summary, library CRUD (all 6 *Arr types,
validation failures, not-found handling), and persistence round-trips
(including that the activity table starts empty and is only ever
populated by explicit writes, never seed data).

### Docker

```bash
docker compose -f compose.v2.yml up --build
```

This builds `Dockerfile.v2` (context: repo root, copies only `v2/`),
tags the image `huntarr-v2:preview`, runs container `huntarr-v2`, and
binds host port **9706** (distinct from v1's 9705). The SQLite database
lives at `./data-v2/huntarr_v2.db` on the host (distinct from v1's
`./data/config`) - **v2 never mounts or reads v1's `./data` directory or
database.**

> **Docker was not available in the environment this milestone was built
> in** (no `docker` binary on PATH), so the image build and container
> smoke test above were not executed here. The commands are exact and
> ready to run; local test coverage (`pytest`) and manual `curl` smoke
> tests against the Flask dev server (see below) were used instead to
> verify behavior.

Manual smoke test performed against the dev server (not the container),
confirming: `/health` and `/api/v2/status` return 200 with correct DB/
count data; library create/list/get/update/delete all work end-to-end
over HTTP; API responses never contain a created library's raw API key
(verified with a raw substring `grep`); policy validation rejects
out-of-range values with 400 and accepts valid updates; all four UI pages
and their static assets (`/static/style.css`, `/static/app.js`) return
200.

## Current milestone

Foundation only:
- Layered app skeleton (domain/services/adapters/persistence/api/web)
- Durable SQLite persistence for libraries, policy, and activity jobs
- Full library CRUD with validation and secret redaction
- Automation policy with Balanced defaults, validation, and a
  plain-language summary
- Read-only activity API and durable job state model (no data yet)
- Responsive, clearly-labeled preview UI for all of the above
- Health/status endpoints
- Docker packaging (build/run not verified in this environment - see above)

## Non-goals / current limitations

- **No hunting.** Nothing in this milestone searches an *Arr instance,
  talks to an indexer, grabs a release, or imports a file. The
  `AutomationPolicy` and `ActivityJob` models exist to be consumed by a
  future search engine - none exists yet. The activity table is
  permanently empty until that engine is built.
- No authentication/authorization on the v2 API or UI (matches the scope
  of this preview; v1's auth is untouched and unaffected).
- No outbound HTTP calls to *Arr instances at all - `url`/`api_key` are
  stored and validated for shape only, never dialed.
- No background scheduler, worker process, or queue.
- No migration tooling beyond idempotent `CREATE TABLE IF NOT EXISTS`.
- Docker image build/run was not exercised in this environment (no Docker
  available); commands above are ready but unverified end-to-end.

## Migration safety

- `v2/` is fully standalone: separate dependencies (`v2/requirements.txt`),
  separate database (`data-v2/`, never `data/`), separate Docker image
  (`huntarr-v2:preview` via `Dockerfile.v2`/`compose.v2.yml`), separate port
  (9706 vs v1's 9705), separate container/service name (`huntarr-v2` vs
  `huntarr`).
- No file under `main.py` or `src/` was modified for this milestone.
- v2 never opens, reads, or writes v1's `./data/config` directory or
  `huntarr.db` file - there is no shared state between v1 and v2 in this
  milestone, by design, so both can run side by side safely during
  evaluation.
